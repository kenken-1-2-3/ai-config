# Ground, implement and prove a change

Use the relevant sections for a non-trivial behavior/interface change or an explicit request to deepen a task. Small mechanical edits, Git operations and lookups keep their direct workflow. This reference supplements the active workflow; it does not require a plan document, new skill, extra approval round or workers. Keep the existing source-authority, API-blocker, shared-UI, authorization and project acceptance gates.

## Planning: how, why, sharpen

- **How — before choosing an implementation location:** trace the affected entry point through state/data flow to its outputs and shared owners; identify the existing compatible component or abstraction and one relevant caller/test. Retain precise source anchors in the current spec/plan/handoff instead of a second architecture report. Stop when ownership and the affected contract are established; naming the nearest file alone is insufficient.
- **Why — before changing a boundary, removing a safeguard or simplifying unusual behavior:** inspect the relevant blame/commit patch and linked decision, ticket or test that explains it. Expand to other available primary sources only for a concrete unresolved question. Record what must be preserved, what may change and any unknown rationale; separate evidence from inference. An absent explanation is not proof a safeguard is unnecessary. Do not search every MCP or replay whole histories by default.
- **Sharpen — when the task or its proof is underspecified:** identify the primary material, the domain-specific method/tool and an observable result that could show the work is wrong. Improve depth within the original outcome; leave user-owned product decisions open and use the existing material-decision gate. A standalone prompt-rewrite request returns the rewritten prompt without executing it. For already-authorized work, resolve discoverable facts and continue without requesting approval of the rewritten wording.

## Implementation: architect, arena, tdd

- **Architect — when interface or ownership choices materially affect callers:** use the existing `deep-module-design` skill only when its trigger fits; narrower project skills retain ownership. Establish caller usage, contracts and invariants before filling in implementation. A settled interface or ordinary multi-file edit does not need a fresh architecture exercise.
- **Arena — when consequential alternatives remain unresolved, or explicitly requested:** freeze the same source packet and compare viable approaches against correctness, compatibility, caller burden and verification cost before choosing. Keep the recommended base and only compatible improvements; record rejected tradeoffs in the existing design artifact. Do not average incompatible contracts or silently turn one approach into a larger feature. Parallel candidates, model choices and review must satisfy `rules/agent_dispatch.md`; this reference grants no new delegation exception or automatic worktrees. If independent candidates are not permitted/available, compare inline and label that limitation rather than claiming multi-model consensus.
- **TDD — when new feature code has existing test infrastructure under `rules/skill_trigger_guard.md`, or the user explicitly requests test-first work:** derive the expected observable behavior from the approved requirement before production edits. Run a focused test and confirm it fails for the intended missing/wrong behavior, implement, then run it again with the required nearby regression checks. Missing dependencies, syntax errors and broken setup are not a valid red result. Never weaken locked expectations or introduce infrastructure just to satisfy this sequence.
- **For other fixes:** use the existing project's required verification, preferring a cheap failing-before/passing-after reproduction when practical. Do not manufacture a test for a prose/mechanical edit or use assertions that merely mirror implementation. If no failing-before run is available, state that limit and retain all required after-change gates; inability to show red is not permission to skip them.

## Verification: three evidence gates

These are evidence dimensions, not three mandatory reviewers. Establish the affected scope before implementation, then check it against the final diff. Mandatory project checks remain mandatory even if a risk analysis calls the change small.

### 1. Exercise the real path with a reusable recipe

- For affected behavior, use the existing project verification instructions and actual user entry point (UI, CLI, service or library public API). Capture the action and result, including required Network/persistence evidence; internal setters, a final screenshot alone or fixtures cannot prove the real integration. For rule/document changes, use routing/installation checks and realistic decision scenarios rather than pretending to run an application journey.
- When a necessary verification journey is undocumented or repeated setup has caused rework, extend its existing project skill/reference within the authorized scope. Keep one owner, with exact startup/readiness checks, expected build/environment, route/controls or commands, prerequisites, expected outcomes, evidence destination and task-owned cleanup. Record observed selectors and commands, not invented examples; keep credentials out. Link the recipe from the existing project verification entry point. Do not auto-create a separate verification skill/catalog for every feature or edit another project's guide without authorization.
- Before relying on a new/changed recipe, execute its affected journey end to end and verify evidence survives cleanup. Unrun steps remain `DRAFT / UNVERIFIED`; one exercised journey does not certify other routes, states or environments. Reuse setup and prior evidence only under `rules/agent_dispatch.md` and the applicable project verification rules.
- When a changed route, shared dependency, command, prerequisite or expected behavior touches a maintained recipe, compare its covered paths and last verified source/environment with the candidate and dirty diff. Refresh affected journeys and mandatory final gates; keep unchanged coverage under the existing reuse rules. Check for newly required entry points missing from the recipe. An unknown impact remains unverified, not a clean audit.
- Classify a failed journey before editing: stale instructions, a harness/tool failure, or a product regression. Correct instructions only from authoritative current behavior requirements; do not rewrite expected outcomes to match a regression. Repair a harness within scope and rerun its journey; report product bugs without expanding a verification-only task. Retain per-journey source/environment identity, actual commands/actions, evidence paths and unresolved prerequisites in the existing owner record. The ai-config instance is [the skill validation recipe](skill-validation.md); do not create parallel feature catalogs.

### 2. Prove the safety assumptions beyond the diff

- For changed shared behavior, interfaces or lifecycle, trace the actual consumers and the relevant indirect boundary: serialized/API fields, persisted data, scheduled callbacks, teardown, or pinned dependency behavior. Focus on the failure mechanism; a symbol search or number of edited files does not establish impact.
- State the key assumption each material safety claim depends on and exercise the relevant real code or runtime path with an existing focused check where possible. Record confirmed risks separately from cleared ones, and distinguish source-only reasoning from executed proof. Unproven critical assumptions remain `UNVERIFIED` and follow existing verification/acceptance blockers; they cannot be cleared by confidence or a low risk label.

### 3. Challenge the result and resolve findings

- Use an independent reviewer only when the existing risk gate, project rule or explicit user request requires it. Give the reviewer the intended behavior, exact diff/baseline and necessary source anchors; do not seed it with the author's preferred verdict. Review-only scope does not authorize fixes.
- For each actionable finding, require a concrete contract violation, affected path and source evidence; reproduce it with the smallest safe check when possible. Do not discard a critical static finding merely because a live reproduction is unsafe or unavailable: retain the uncertainty and its blocking implication. Deduplicate by root cause and rerun affected checks after authorized fixes.
- Agreement between models is not proof, and a single reviewer's evidenced finding must not be outvoted. Main owns per-criterion acceptance and the final evidence report, including skipped, blocked and unverified checks. No review verdict authorizes Git operations, deployment or changing frozen requirements.
