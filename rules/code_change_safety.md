# Code Change Safety

- Before deleting or renaming any import, symbol, function, event handler, route, field, config key, or component, search the complete changed file for uses of that same binding and search relevant repository call sites when the symbol can be referenced outside the file. A partial file read or narrow search is not evidence that a symbol is unused. This gate has no import-only, cleanup, or small-change exception.
- Delete only when that binding has zero remaining references, or when every remaining reference is intentionally updated by the requirement. Same-spelled symbols bound independently in other scopes do not block the deletion. Before commit, inspect every deleted line in the staged diff and account for it; an unexplained or unrelated deletion blocks the commit.
- For Vue or TypeScript changes, when the repository provides a permitted project-defined type-check command, run it, such as its `ts-check` script using `vue-tsc`; do not substitute a direct compiler command that the repository rules prohibit. If no permitted project-defined type-check command exists, record `TYPECHECK_UNAVAILABLE`, do not invent or install one, and run a risk-equivalent focused static check capable of detecting the edited failure class plus any applicable runtime smoke. This fallback must not be reported as a passing type-check. Run the focused tests required by the edited risk plus any project-required build, lint, or format checks. If the baseline already fails, capture before and after diagnostics and reject any new error. Build, lint, format, and source-string assertions do not substitute for type-check.
- Do not dismiss a failing verifier as pre-existing without before/after evidence, and do not replace a failing broad verifier with a narrower check that cannot detect the edited risk.
- When changing user interaction or a dependency used during component setup, including imports, stores, composables, and event registration, perform a component or browser runtime smoke test of the affected behavior. If an applicable required verifier above is missing, blocked, or fails, mark the affected change `UNVERIFIED`; commit, merge, push, deploy, and release are blocked until the user explicitly accepts that exact verification gap. `TYPECHECK_UNAVAILABLE` alone is not a failed verifier only when the prescribed risk-equivalent static check and every applicable runtime smoke have completed and passed.
- A small or import-only change is not by itself a reason to skip the applicable type-check or runtime smoke.
